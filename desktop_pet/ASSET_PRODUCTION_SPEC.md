# 小桃桌宠素材生产规范 v1.2

适用项目：`desktop_pet`。编制日期：2026-10-19。

本文用于指导角色定稿、动作视频生成、透明素材加工、程序导出与验收。当前已接入待机、思考、挥手、左右行走和开心六个透明 WebM，后续动作仍按本规范扩充。

文中的“现状”来自本仓库代码与实际素材；“新版规范”定义重新生成的视频素材。制作目标为 3:4 竖版、960 × 1280 制作母版、720 × 960 正式播放视频；当前使用的源视频实际只有 720 × 960，不将放大文件标记为原生高清母版。

## 1. 首版方案

采用以下生产链：

**角色参考图定稿 → 生成 960 × 1280 动作源视频 → 抠像与边缘修整 → 保留同尺寸透明加工母版 → 导出 720 × 960 透明动作视频 → 接入新版视频播放器。**

每个动作交付一个独立视频文件。透明 PNG 帧序列作为加工和修整的中间材料，GIF 用于快速预览。当前正式格式为 VP9 Alpha WebM、720 × 960、24 fps、无音轨；播放器强制使用 libvpx-vp9 解码输出 RGBA，文件扩展名不能作为透明播放可用的依据。

此次重新生成素材，不以旧图集的尺寸、比例或行列数限制新版。程序已通过独立视频播放器实现透明绘制和动作适配，旧图集保留为完整后端回退。

依据：`assets/sprite_config.json`、`animation/sprite_player.py`、`app/desktop_pet_window.py`、`character/conversation_state.py`、`utils/sprite_mask.py`。

| 项目 | 当前实际行为 | 对新素材的要求 |
| --- | --- | --- |
| 素材文件 | 配置指向 `assets/spritesheet.webp`；实际为 3072 × 2496，带 Alpha | 以实际配置为准，旧说明中的其他图集名称不作为当前路径 |
| 裁切方式 | 每帧 192 × 208；一行一个动作，从第 0 列开始连续取帧 | 这是旧图集约束，新版使用独立的 3:4 动作视频 |
| 当前播放 | 每个动作 12 或 16 帧，配置帧率为 4–12 fps | 增加真实连续帧，并同步修改帧数与帧率 |
| 播放器 | `QPixmap` 读取静态图集，`QTimer` 推进裁切帧 | 新版需要视频播放适配，不能只修改素材路径 |
| 动作切换 | 切换时从目标动作第 0 帧开始；结束后回退；没有过渡混合 | 起始姿态统一，常用动作允许随时被打断 |
| 窗口尺寸 | 随显示帧宽高调整，浮动控件跟随窗口 | 所有动作必须使用相同完整画布，禁止逐帧裁紧 |
| 显示缩放 | 示例配置 `ui.scale = 0.6`，192 × 208 显示为约 115 × 124 | 新版独立设置逻辑显示尺寸，不直接把旧缩放值乘到 720 × 960 上 |
| 缩放采样 | 整数倍放大使用快速采样，缩小及非整数倍使用平滑采样 | 视频渲染使用平滑缩放，结合设备像素比保留清晰度 |
| 左右移动 | 窗口用 1200 ms 完成一次平滑位移 | 跑步视频原地循环，不能把横向位移烘焙进帧内 |
| 自主跳跃 | 窗口已提供上升、下降轨迹，时长取动作时长 | 跳跃帧主要表现屈膝与伸展，不能再做一次大幅整体上移 |
| 点击区域 | Alpha 大于 0 的像素均进入人物窗口掩码 | 远处透明噪点、雾状残边也可能截获点击，必须清理 |
| 动作复用 | `leaf-hug` 当前与 `review` 共用第 8 行；第 11 行未被实际配置使用 | 新完整包为 `leaf-hug` 制作独立动作视频，不再依赖行号 |

`running` 是历史动作键，现用于思考与部分对话表现，不表示左右跑动。左右跑动只使用 `running_left`、`running_right`。

当前 `action_duration_ms()` 对普通循环动作返回一帧间隔，只有非循环或指定单轮时才返回整段时长。新版应区分完整素材时长、默认循环和强制单轮，并根据媒体时间戳及结束事件处理跳跃、退出与回退；不能把旧函数的普通循环返回值用于视频时长。

## 3. 角色统一规则

### 3.1 首版形象基线

默认沿用现有角色的识别元素：棕色长发、学院风服装、浅色上衣、深色裙装、橙色枫叶，以及温柔、克制的陪伴感。升级重点是轮廓、表情和动作连续性。

首版建议采用线条清楚、阴影简洁的 Q 版二维插画风。当前桌面显示较小，眼睛、手势和枫叶应优先可辨，避免依赖细发丝、细密花纹或细小文字。此处是制作默认方向，最终发型、服装细节与配色以定稿参考图为准。

业务角色名沿用配置中的“小桃”；图集元数据里的 Maple / 枫叶同学视为历史标识，不用于另起一套角色。

### 3.2 批量生成前必须锁定的参考材料

在同一份制作记录中保存以下参考，不允许只凭一段文字分别生成十二个动作：

- 正面全身标准站姿：所有正面动作的共同起点。
- 左右侧向或四分之三视角参考：供跑步使用，确认发型、服饰和枫叶的位置。
- 表情参考：平静、微笑、思考、轻微失落、困倦；脸型、眼睛大小与头身比例保持一致。
- 色板与细节说明：发色、瞳色、衣服、鞋袜、枫叶的固定颜色；明确枫叶是手持物还是服饰配件。

先在参考图上确定枫叶的固定位置和持握手，再生成动作。持握手不能在相邻帧无故改变，手指不能与枫叶合并，挥手时不能多出一只手。左右跑步优先分别制作；只有角色细节确实对称时才允许镜像，并在制作记录中注明。

### 3.3 固定站姿与镜头

镜头固定，无推拉、摇移、变焦、透视变化和景深变化。人物全身入画，光线与阴影方向固定。所有动作使用同一参考图版本，不能在动作中途换脸、换衣或改变头身比例。

标准站姿记为 **S0**：正面、平静、双脚自然落地，手部与枫叶处于定稿参考图规定的位置。首版不加入地面、桌面、文字、对话气泡或外飘粒子；对话文字由程序显示。

## 4. 画布、锚点与透明度

| 参数 | 新版规范 |
| --- | --- |
| 画面比例 | 全包统一为 3:4 竖版，方形像素，无旋转元数据依赖 |
| AI 源视频 | 960 × 1280 px；绿幕等纯色背景，保留原始下载文件 |
| 透明加工母版 | 960 × 1280 px；以 RGBA、sRGB 的无损透明帧序列保存，或使用经验证的等效无损带 Alpha 母版 |
| 正式播放视频 | 720 × 960 px，真实 Alpha；从透明母版统一按宽高各 75% 缩小一次 |
| 可选高清播放视频 | 960 × 1280 px，真实 Alpha；需要时从同一母版导出，构图和时间轴与正式版一致 |
| 坐标定义 | 左上角为原点，x 向右，y 向下；下述数值为正式播放画布坐标 |
| 标准人物占比 | S0 人物高约 80%，即 768 px；母版中约 1024 px |
| 标准头顶与脚底 | 头顶约 y=96，脚底约 y=864；母版对应 y=128、y=1152 |
| 站立锚点 | 双脚落地区域中点约为 `(360, 864)`；对应母版 `(480, 1152)` |
| 动作安全边距 | 所有有效像素距左右边缘至少 36 px、上下边缘至少 48 px；母版对应 48 px、64 px |
| 动作内布局 | 固定画布、固定缩放、固定锚点，呼吸和肢体运动保留自然小幅变化 |
| 帧率 | 正式版统一 24 fps，固定帧率；透明母版各帧为完整画布，视频编码可使用帧间压缩 |
| 背景 | 真实 Alpha；空白区域 Alpha 必须为 0，人物轮廓允许半透明抗锯齿 |
| 阴影 | 首版不加地面投影；人物自身阴影保留，避免新增大块可点击区域 |

归一化时，为整个动作包确定一个统一缩放系数；各动作可做一次固定平移对齐。不能按每帧包围盒分别缩放或自动居中，否则呼吸、挥手时人物会忽大忽小或左右晃动。

S0 对齐后，动作起点、终点与标准参考的脚底位置误差不超过正式画布中的 3 px，头部尺度差异不超过 2%。这些是制作验收容差，未由当前程序自动检测。跑步腾空阶段与屈膝动作按设计允许变化，检查的是身体根部的意外漂移。

安全边距必须容纳挥手、头发、裙摆和枫叶的最大外扩；如果动作越界，应先改动作幅度或全包构图，不能只缩小该动作。像素为 0 起算时，720 × 960 画布的有效像素应落在 x=36–683、y=48–911 内。标准站姿的上下留白各约 10%，用于动作外扩；不要求动作中每一帧的人物高度都严格等于 80%。

3:4 更适合全身人形构图，但不保证完全横向伸展双臂等大幅动作一定能容纳，必须先验收最大姿态。正式交付保持统一 3:4 画布；不做逐帧裁切，也不为各动作设置不同裁切框。

去掉绿色污染、白边、黑边、背景残块与远离人物的半透明噪点，同时保留发梢、衣缘与手指。现有浅色背景修复仅是兜底，不能作为正式抠像流程。

### 4.1 桌面显示与人物有效区域

720 × 960 是视频像素尺寸，不是窗口必须占用的桌面尺寸。新版初始显示建议以 240 × 320 逻辑像素为小样基准，可另外检查 180 × 240、300 × 400；人物占高 80% 时，对应可见人物高度约为 256、192、320 逻辑像素。最终默认大小通过桌面预览确定。

视频像素、窗口逻辑尺寸和 Windows 显示缩放分别处理，不直接继承旧 `ui.scale = 0.6` 的尺寸语义。Qt 将窗口逻辑坐标与图像像素区分，并使用设备像素比关联两者，依据：[Qt 高 DPI 说明](https://doc.qt.io/qt-6/highdpi.html)。

新版应以固定脚底锚点和人物有效区域计算气泡、菜单位置与屏幕移动边界，避免围绕透明留白定位。人物有效区域可以记录为全包动作范围，但不能通过逐帧自动居中改变人物位置。点击区域仍根据实际 Alpha 处理。

## 5. 动作清单与节奏

下表是**新版视频包目标**。保留现有动作键以衔接业务调用，每个键对应独立视频，不再规定图集行号。全部采用 24 fps，表中帧数与时长是首轮节奏目标，小样通过后再固化到动作描述清单。

当前左行采用 216 帧、右行采用 269 帧完整单次版本，具体行为见 1.2；下表的一秒循环步态仍为后续制作目标。

| 动作键 | 内容与用途 | 帧数 / 名义时长 | 默认循环 | 批次 |
| --- | --- | --- | --- | --- |
| `idle` | 平静呼吸、轻眨眼；常驻待机 | 48 / 2 s | 是 | 小样 |
| `running_right` | 面向右的原地小跑 | 24 / 1 s | 是 | 第二批 |
| `running_left` | 面向左的原地小跑 | 24 / 1 s | 是 | 第二批 |
| `waving` | 抬手、招手、收手；问候与退出 | 48 / 2 s | 否 | 小样 |
| `jumping` | 屈膝、伸展、收腿、落地恢复 | 24 / 1 s | 否 | 第二批 |
| `failed` | 轻微失落，随后恢复平静 | 36 / 1.5 s | 否 | 第三批 |
| `waiting` | 温和注视、轻歪头；等待输入或回应 | 48 / 2 s | 是 | 第二批 |
| `running` | 原地思考，视线小幅变化 | 48 / 2 s | 是 | 小样扩展 |
| `review` | 仔细端详；正式问答、剪贴板、截图等 | 48 / 2 s | 是 | 第三批 |
| `happy` | 轻微开心摇摆，不做全身大位移 | 36 / 1.5 s | 是 | 第三批 |
| `sleepy` | 缓慢闭眼、轻点头，回到清醒站姿 | 48 / 2 s | 是 | 第三批 |
| `leaf-hug` | 抱近枫叶再回到标准持握位置 | 48 / 2 s | 是 | 第三批 |

合计 12 段视频、480 帧有效画面、20 秒有效动作。默认循环为“是”的动作仍要能播放一轮后回到 `idle`，因为菜单测试、对话与自主动作可能通过 `force_single_cycle=True` 强制单轮。

### 5.1 单次动作

`waving`、`jumping`、`failed` 第一帧从 S0 出发，最后一帧回到 S0。动作应有起势、主体、恢复三个阶段，不能结束在手举到一半、腾空或低头未恢复的状态。

`waving` 的 48 帧参考节奏：第 0–5 帧自然抬手，第 6–29 帧完成两次小幅招手，第 30–41 帧收手，第 42–47 帧回稳。最后一个稳定段包含自然细微变化，避免长时间复制同一张图。

`jumping` 的视觉起跳、最高点和落地分别靠近 0%、50%、100% 时间位置，以配合现有窗口轨迹。首版将身体根部保持在固定基准附近，仅通过关节姿态表现腾空；不要在透明帧中再加入大幅整体升降。普通对话也会单独播放此动作，因此还要验收窗口不移动时的表现。

### 5.2 循环动作

首尾相邻播放时，头发、裙摆、手部、表情与运动方向连续。导出循环区间采用“包含起点、不重复终点”，避免重复边界帧造成停顿。

正面循环的起点应接近 S0，末帧应能自然接回起点。由于现有代码允许在任意帧切换动作，主体姿态应保持克制；不能只让首尾好看，中途却大幅转身或弯腰。

左右跑步以步态循环为主，起点可以是固定接触姿态，不强制为正面 S0。必须单独检查 `idle → 跑步 → idle` 的朝向突变与脚底跳变。如果无法接受，应在后续播放器中增加转身或起停过渡，不能宣称仅靠循环素材已解决所有衔接。

源视频允许长于有效动作，方便选段。工具只能输出固定时长时，保留开头与结尾的稳定段，再提取中间完整动作；不要把 10 秒素材全部塞进最终动作，也不要靠大幅加速压成 2 秒。

若角色含绿色服装、眼睛或道具，应在整包生产前选定另一种不与主体冲突的纯色背景，并统一记录。优先选择能输出原生 3:4 的生成设置；工具不支持时，在其他比例中预留完整 3:4 区域，再对整段视频使用固定裁切框，保持人物全身与动作空间。不能拉伸人物、逐帧跟踪裁切，或把低分辨率输出放大后记为原生 960 × 1280。记录裁切后的实际有效分辨率，若不足目标则更换生成设置或另行评估清晰度。

生成条件中尽量避免水印覆盖人物。人物区域被遮挡或带有无法干净分离的文字时重新生成可用版本，不能用局部涂抹造成服装、头发在相邻帧跳变。

## 7. 后处理顺序

1. **保留原始文件。** 记录来源、实际分辨率、帧率、时长和使用条件；不要覆盖原下载文件。
2. **筛选有效片段。** 排除换脸、变形、遮挡、越界和不完整动作；先验动作质量再花时间抠像。
3. **抠像与去色污染。** 导出带 Alpha 的透明序列，必要时逐帧修整；绿幕视频本身不具有透明背景。
4. **建立统一画布。** 根据全包最大动作范围确定缩放与站位，输出 960 × 1280、3:4 的透明加工母版；保留完整透明边缘与统一锚点。
5. **确定节奏与帧数。** 选定循环边界或完整单次动作，统一到 24 fps。补帧必须复核手指、枫叶和轮廓；大量重复帧不能作为平滑处理。
6. **导出正式视频。** 从透明母版统一缩小到 720 × 960，按动作导出 24 fps、无音轨的透明视频；检查编码后的 Alpha、半透明边缘与颜色。可选高清版使用同一母版与时间轴。
7. **制作预览。** 输出深底、浅底、棋盘格预览，保留正常速度版本；需要时补充慢放和接缝逐帧图。
8. **打包与接入。** 核对视频与动作描述清单，在候选播放后端中验证解码和透明绘制，再进行真实窗口中的动作和交互验收。

本规范不绑定生成平台、剪辑软件或抠像工具。每步都应能从原始文件或中间母版重新导出，不能只保留一个压缩 GIF。

## 8. 文件交付与命名

### 8.1 文件用途

| 文件类型 | 交付用途 | 当前可否直接播放 |
| --- | --- | --- |
| 原始 MP4 等视频 | 生成原件与追溯依据，通常不含 Alpha | 否 |
| 960 × 1280 无损透明母版 | 加工、修整、重新导出依据，优先保存完整 PNG 帧序列 | 否，属于制作材料 |
| 720 × 960 透明动作视频 | 新版正式运行素材，一动作一文件，VP9 Alpha WebM | 是，当前三个动作已接入 |
| 960 × 1280 透明动作视频 | 可选高清运行档，不等同于未抠像的源视频 | 尚未配置高清素材 |
| GIF | 快速观看节奏的预览，可附深浅底两个版本 | 否，现有播放器未接入 |
| 旧静态 WebP 图集 | 现有版本运行与迁移期间回退使用 | 是，仅限旧播放器 |

GIF 使用颜色表和透明色索引，不能表达连续的半透明边缘，因此首版把它作为预览文件。依据：[GIF89a 规范](https://www.w3.org/Graphics/GIF/spec-gif89a.txt)。

当前依赖为 `PySide6-Essentials`、`requests` 与 `imageio-ffmpeg==0.6.0`。视频后台通过随包 FFmpeg 显式选择 libvpx-vp9 输出 RGBA，不要求系统安装 FFmpeg。新增素材仍需验证解码、Alpha 输出、循环接缝、单轮结束和资源释放。

当前程序不使用 QMovie 播放 WebM；由后台解码交付 QImage，主线程绘制并从实际 Alpha 更新逻辑坐标点击掩码。QMovie 的接口范围参考：[Qt QMovie 文档](https://doc.qt.io/qt-6/qmovie.html)。

以下为未来交付目录约定，本次文档编制不创建这些目录。原视频、帧序列、预览与制作记录建议放在仓库外的素材工作目录；当前忽略规则会放行 `desktop_pet/` 下的大部分文件，不能把原件直接堆进去。

### 8.3 正式视频导出与动作描述清单

- 每个动作一个文件，正式档均为 720 × 960、24 fps、3:4，无音轨；不得混用不同画布或不同人物缩放。
- 不拼接大图集，不将 GIF 或普通绿幕 MP4 作为正式透明视频交付。
- 编码后重新解码检查真实 Alpha，包括空白、实体与半透明边缘；必须在目标播放后端通过深浅底预览。
- 每段首帧能独立开始播放；检查从零启动、连续循环、切换动作、强制单轮与结束回退时无黑帧、残帧、累积拖影或额外停顿。
- 同一动作标准档与高清档的帧率、帧数、时长、循环边界完全一致；锚点和有效区域使用归一化坐标，或按分辨率等比例换算。
- `actions.json` 至少记录：清单版本、角色包版本、各档尺寸、动作键与相对视频路径、帧率、有效帧数、核实后的素材时长、默认循环、回退动作、脚底锚点、人物有效区域、编码信息及文件校验值。
- 播放器实现时定义并校验该清单的具体字段结构。目前 `actions.json` 是拟定交付接口，不能把它直接当作现有 `sprite_config.json` 使用，也不立即覆盖 `DEFAULT_SPRITE_CONFIG`。

本规范只定义目标，不立即创建动作清单、覆盖现有 `spritesheet.webp` 或修改现有配置。迁移完成前保留旧素材与旧播放路径供回退。

## 9. 性能预算与升级条件

新版按动作解码视频，采用有限缓存并及时释放不用的解码资源。当前播放器一次加载全部图集帧的方式不适用于新版高分辨率视频，原图集的列数与内存估算不再作为新包预算。

720 × 960 每帧有 691,200 像素，比先前讨论的 960 × 540 多约 33%。按 RGBA 每像素 4 字节估算，正式版单帧约 2.64 MiB，960 × 1280 高清版单帧约 4.69 MiB；整包 480 帧若全部展开为正式版 RGBA，约需 1265.63 MiB。因此不能将整包预解码并常驻内存。

这些数值只是像素数据规模，不能代替实际进程内存、文件体积或解码耗时；解码格式、帧缓存、渲染副本和后端都会影响结果。视频文件较小、透明区域较多也不保证播放占用较低。

首版性能门槛作为小样实测目标：

- 在同一台机器、相同业务配置下，记录旧版与视频版的加载耗时、首帧延迟、空闲 CPU、GPU 和进程内存；新视频另在相同逻辑显示大小下比较标准档与高清档。
- 常驻 `idle` 连续播放 5 分钟不出现肉眼可见的周期性卡顿；采样帧间隔时不应反复超过两个目标帧周期，约 83 ms。
- 加载与循环切换期间能正常拖动、打开菜单和输入；连续切换动作后内存不持续增长。
- 标准视频版的进程稳定内存增量暂以不超过旧版 200 MiB 为小样预算，解码器与渲染资源一并计入；若超预算或卡顿，先调整后端、缓存与渲染方式，再扩充素材。GPU 占用另行记录，不能只看进程内存。

当前三个素材已验证真实 Alpha、帧数、循环与单次结束路径；上述跨设备 CPU、内存与 GPU 预算仍需在目标设备验收，不承诺所有设备都能稳定达到 24 fps。播放器按固定帧率和实际经过时间调度，名义帧周期约 41.67 ms，不以 41 ms 累加推算结束；退出由实际末帧结束事件驱动。

优先验证 720 × 960 标准档。只有标准档的透明绘制、常驻循环与资源释放通过后，再评估 960 × 1280 高清档；高清模式不通过时仍可保留高清制作母版，并继续使用标准运行视频。

## 10. 验收清单

### 10.1 文件与视觉验收

- [ ] 制作母版均为 960 × 1280、正式视频均为 720 × 960，3:4 构图与 75% 缩小关系一致，未拉伸或以低清放大冒充母版。
- [ ] 母版帧序列连续编号；各视频实际帧数、帧率、时长、无音轨及循环标记与动作清单一致，全部路径和校验值有效。
- [ ] 编码后可在目标后端解码出真实 Alpha，标准档与可选高清档构图、锚点和时间轴一致。
- [ ] 透明背景的空白区 Alpha 为 0，无远处噪点；头发、手指、枫叶与服装边缘完整。
- [ ] 在白、深灰、棋盘格背景上观看，无绿边、白边、黑边或色块闪烁。

- [ ] `idle → waving → idle`：问候、双击与退出时动作完整，退出等待与实际视频结束同步。
- [ ] `idle → waiting → running/review → idle/failed`：输入、思考、正常回复及失败时切换合理。
- [ ] 左右跑步随窗口位移，视频自身不再横向移动；移动提前结束或被交互打断时不跳回旧动作。
- [ ] 自主跳跃与窗口轨迹同步，不出现双重升降；单独播放跳跃也不出现裁切或悬空残留。
- [ ] 循环动作被强制只播一轮时，能够结束并回退；任意中间帧切换时无明显身体位置突变。
- [ ] 首帧、循环接缝与动作切换无黑底、闪白、残帧和累积拖影；损坏或缺失视频能进入明确的恢复状态。
- [ ] 气泡、菜单与屏幕边界按人物有效区域定位，透明留白不导致气泡远离人物或人物无法贴近屏幕边缘。
- [ ] 深浅桌面背景、拖动、点击透明区域、气泡与菜单跟随、缩放后的人物边缘均正常。
- [ ] 模型请求完成时，旧回调不会覆盖新交互动作；保留 `_set_pet_action()` 与 `_finish_pet_action_if_owned()` 的动作归属规则。
- [ ] 加载、5 分钟常驻、连续切换与退出通过第 9 节性能目标，记录实际数据。
- [ ] 切换动作、关闭窗口后解码线程、文件句柄与渲染资源正确释放，无后台残留任务。

正式改动素材或播放器后，使用项目实际虚拟环境运行现有精灵加载、渲染和动作冲突相关测试，并针对新增视频路径验证解码、透明绘制、结束事件和资源释放；还需检查退出与自主跳跃。文档编制阶段不启动应用或调用模型。

## 11. 第一轮制作任务

先做 **一张 3:4 正面标准参考图，加 `idle`、`waving` 两个动作**，分别验证常驻循环、单次动作、人物占比、挥手最大范围与两者切换。两段都交付 960 × 1280 原始视频及透明加工母版、720 × 960 正式透明视频与深浅底预览。`running` 作为小样扩展，在基础验证通过后补充思考循环。

先在独立播放验证中确定透明视频编码与解码后端，再安排主窗口适配。小样通过后，按第 5 节完成其余动作。小样不完整时，明确展示已验证动作，不把视频塞进旧图集配置，也不假定旧播放器已经支持新视频。

只有完整包与新版播放器共同通过验收，才切换正式运行路径。保留原角色包与旧播放器的可回退版本，并记录接受的形象、布局、节奏、编解码参数与性能结果，作为下一批生成的固定基线。
